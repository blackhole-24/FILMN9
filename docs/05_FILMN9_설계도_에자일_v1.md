## 애자일 프레임워크

### 적용 방법론
- **Scrum** 기반 + **Kanban** 보드 병행
- Sprint 주기: **1주 (7일)**
- 데일리 스탠드업: 매일 10분 (어제 한 것 / 오늘 할 것 / 장애물)
- 스프린트 리뷰: 매 Sprint 마지막 날 (완성된 기능 데모)
- 스프린트 회고: 스프린트 리뷰 직후 (Keep / Problem / Try)

### 스크럼 역할

| 역할 | 담당 | 책임 |
|---|---|---|
| **Product Owner** | 이형주 | 백로그 우선순위, 비즈니스 가치 결정 |
| **Scrum Master** | FILMN9 팀 리드 | 프로세스 진행, 장애물 제거 |
| **Dev Team** | FILMN9 팀 전체 | 기능 개발, 테스트, 배포 |

### 백로그 관리

```
Product Backlog (전체 기능 목록)
          │
          ▼ Sprint Planning (선택)
Sprint Backlog (해당 스프린트 목표)
          │
          ▼ 개발 진행
Sprint Review (데모)
          │
          ▼ Sprint Retrospective (회고)
          │
          ▼ 다음 Sprint
```

## 애자일 vs. 워터폴 비교

| 항목 | 워터폴 | 애자일 (FILMN9 실제) |
|---|---|---|
| 요구사항 변경 | 어렵고 비용 높음 | Sprint 계획에서 조정 가능 |
| 고객 피드백 | 최종 단계에서 수렴 | 매 Sprint 리뷰에서 수렴 |
| 위험 발견 시점 | 테스트 단계 (늦음) | 초기 Sprint에서 발견 가능 |
| 배포 가능 제품 | 모든 Phase 완료 후 | 매 Sprint 후 동작하는 버전 |
| FILMN9 적합도 | △ (PoC라 요구사항 유동적) | ✅ (빠른 피드백 반영 가능) |

### 왜 FILMN9에는 애자일이 더 적합한가

1. **불확실성**: PoC 단계에서 어떤 기능이 실제 유용한지 미지수 → Sprint 단위로 검증
2. **빠른 변경**: NAVER 영업비용 구조 같은 예상 못한 예외 → 다음 Sprint에서 즉시 대응
3. **데모 압박**: 3주 안에 시연 가능한 결과물 필요 → Sprint 우선순위로 최소 기능 집중
4. **소규모 팀**: 전체 설계를 미리 확정하기 어려운 팀 규모
