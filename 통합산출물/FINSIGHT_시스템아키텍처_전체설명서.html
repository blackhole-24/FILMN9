2026-06-14 · 운영 FILMN9 Inc. · 발표/이해용

1한 문장 요약

FINSIGHT는 국내 상장사 약 2,600개의 재무·기업가치·AI 분석을 한 화면에서 보여주는 서비스입니다. 모든 숫자는 DART 같은 공식 출처에서 자동으로 끌어와 데이터베이스에 쌓아두고, 사용자가 종목을 열면 그 데이터를 꺼내 화면에 그립니다. (검증 안 된 값은 만들지 않는다 = NO-MOCK)

23개의 층으로 나뉘어 있습니다

건물처럼 층이 나뉘어 있다고 생각하면 쉽습니다. 각 층은 자기 일만 합니다.

① 프론트엔드 (화면 층) — Next.js
사용자가 보는 웹 화면. 종목 페이지의 3개 탭(기업개요·밸류에이션·AI챗봇). 데이터를 직접 안 만들고, 아래 백엔드에 "이 종목 데이터 줘"라고 요청해서 받은 걸 예쁘게 그립니다. (포트 3000)
② 백엔드 (중간 다리 층) — FastAPI
화면과 데이터 사이의 다리. 프론트가 요청하면 데이터베이스·파일에서 꺼내 가공(계산·정렬·없으면 폴백)해서 JSON으로 돌려줍니다. 예: "부채비율" 같은 건 여기서 계산. (포트 8090)
③ 데이터 층 — DB 4종 + 파일
실제 데이터가 사는 곳. 성격이 달라서 4가지로 나눠 저장합니다(아래 4번).
💡 왜 나눌까? 화면 바꾼다고 데이터가 깨지지 않고, AI(무거운 챗봇)가 본 서비스를 느리게 하지 않도록 분리해서 안정성과 비용을 통제하기 위해서입니다.

화면Next.js가 그림
예시 A — 손익흐름도(Sankey): "미리 그려둔 그림"
매번 그리면 느리니까, build_sankey_v3.py가 전 종목 2,654개를 HTML 그림으로 미리 만들어 outputs/sankey/{종목}_sankey.html에 저장해둡니다. 사용자가 손익흐름도 탭을 열면 FastAPI(/sankey/{종목})가 그 파일을 그대로 보내고, 화면은 그걸 표시합니다. → "그때그때 그리는 게 아니라, 이미 그려둔 파일을 꺼내 보여주는 것".
예시 B — 재무제표 3년치: "실시간 DB 조회"
DART에서 받은 재무를 financial_detail 테이블(95.6만 행)에 쌓아둡니다. 재무상태표 탭을 열면 FastAPI(/api/financial_detail/{종목}/BS)가 그 종목의 3개년(2025/24/23)을 그 자리에서 꺼내 표로 정리해 보냅니다.

→ 즉 기능마다 방식이 다릅니다: 사전생성(파일) vs 실시간 조회(DB) vs 외부 실시간 호출(주가·뉴스). 어느 방식인지는 데이터 원천 지도 v2에 모듈별로 표기돼 있습니다.

핵심: "한 DB로 다 하지 않는다." 표는 표 DB, 문서는 문서 DB, 벡터는 벡터 DB, 파일은 파일 — 각자 잘하는 곳에.

6개발 과정 — 왜 이 순서로 만들었나

  • 킥오프~S1(4/22~): 헌장·페르소나·기획서·요구사항 — "무엇을 누구를 위해"
  • S2(4/29~5/9): 밸류에이션 엔진 MVP(WACC·DCF·멀티플) — 가장 어려운 계산부터
  • S3(5/12~5/22): 기업개요·AI 히스토리 브리핑·화면(Next.js)·API(FastAPI)·1차 배포
  • S4(5/26~6/5): 재무 정확성(3개년)·전수화·관리자 페이지
  • S5(6/8~6/19): DB 클라우드 이관·NO-MOCK 전수검증·AWS 배포 — 신뢰성과 배포

전략: 리스크 큰 것(밸류 계산) → 데이터 신뢰성 → 클라우드 순. "되는지부터 증명하고, 정확하게 만들고, 세상에 올린다."

7관통하는 원칙 — NO-MOCK

검증 안 된 숫자·문장은 단 하나도 만들지 않는다. 모든 값은 DART 등 출처 기반. 없으면 "데이터 없음"으로 정직하게 표기. → 이게 FINSIGHT의 최대 차별점이자, 관리자 페이지(신뢰도 검증)로 직접 증명하는 부분입니다.
